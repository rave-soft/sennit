# Технический долг

Что осталось незакрытым после форка Crush, ребрендинга и удаления внешних
сервисов. Каждый пункт — с причиной и понятным следующим шагом, чтобы к нему
можно было вернуться без повторного расследования.

## Отключённые тесты

### Кросс-процессное обновление OAuth-токена — исправлено

`internal/config/refresh_singleflight_test.go`

Раньше `InProcessSingleFlight`, `CrossProcessAdopt`,
`StalePeerBorrowsRotatedRefreshToken`, `IgnoresOlderDiskToken` были отключены
через `t.Skip`. Все четыре снова включены и проходят, в том числе под
`-race`. Затронуло два независимых дефекта фикстуры, оба в тестовом коде, не
в логике обновления токена:

1. **Провайдер вне встроенного каталога.** Фикстура держала провайдера
   `hyper`, которого больше нет в каталоге (Braid использует только
   встроенный, `catwalk.charm.land` не опрашивается). Успешный обмен токена
   пишет на диск только `providers.<id>.api_key` и `providers.<id>.oauth`
   (`ConfigStore.refreshOAuthTokenLocked` → `SetConfigFields`), а затем
   перезагружает конфиг с диска. При перезагрузке `configureProviders`
   валидирует `hyper` как пользовательского провайдера и отбраковывает его —
   на диске нет `base_url`/`models`, взять их неоткуда. Провайдер из
   встроенного каталога (`copilot`) эту перезагрузку переживает: для
   известных провайдеров `type`/`base_url`/`models` каждый раз восстанавли-
   ваются из каталога независимо от того, что лежит в файле. Фикстура
   переведена на `copilot`.
2. **Негерметичность.** `newRefreshTestStore` выставлял `globalDataPath` на
   файл во временной директории, но не переопределял
   `BRAID_GLOBAL_CONFIG`/`BRAID_GLOBAL_DATA`. Перезагрузка конфига читает
   пути через `lookupConfigs`, которая берёт `GlobalConfig()`/
   `GlobalConfigData()` — а те при пустых переменных окружения возвращают
   путь в `~/.config/braid/braid.json` реального пользователя, а не
   тестовый файл. Тесты либо читали чужой конфиг, либо (что как раз и
   ломало все четыре сценария) переживший обмен провайдер не находился при
   перезагрузке вовсе. Исправлено: `newRefreshTestStore` теперь выставляет
   `BRAID_GLOBAL_CONFIG`/`BRAID_GLOBAL_DATA` через `t.Setenv` на свежие
   временные директории (по образцу `scopeb_race_test.go`), а файл
   фикстуры называется `braid.json`, как и путь, который реально читает
   `lookupConfigs`. `t.Setenv` запрещает `t.Parallel()` для теста и его
   предков, поэтому `t.Parallel()` из всех пяти тестов файла убран — они
   делят процессные переменные окружения и не могут безопасно выполняться
   параллельно друг с другом или с любым другим тестом, читающим
   `GlobalConfig`/`GlobalConfigData`.

Логика обновления токена не менялась — оба дефекта были только в фикстуре.

Регресс тех же двух дефектов теперь ловит
`internal/config/path_invariant_test.go`
(`TestConfigPathInvariant_MatchesReloadReadSet`): для нескольких временных
рабочих директорий проверяется, что `configPath(scope)` для `ScopeGlobal` и
`ScopeWorkspace` входит в объединение путей, которые реально читает
`lookupConfigs(workingDir)`, и пути воркспейс-конфига. На момент написания
инвариант выполняется для обоих скоупов — расхождения между «куда пишем» и
«откуда читаем» не найдено.

### Записанные интеграционные кассеты агента — 13 подтестов

`internal/agent/agent_test.go`, `internal/agent/testdata/`

`TestCoderAgent` целиком отключён. Кассеты содержат трафик, записанный Charm
против `hyper.charm.land`, и в телах запросов зашиты полная схема инструментов
и системный промпт того времени — включая имена `crush_info` и `crush_logs` и
старое название продукта. После ребрендинга ни один запрос не совпадёт, а
перезаписать записи без ключа от сервиса Charm невозможно.

Инфраструктура для перезаписи готова (сама перезапись — нет, в этом окружении
нет ни локального LLM-эндпоинта, ни ключей). `hyperBuilder` в
`internal/agent/common_test.go` заменён на `openaiCompatBuilder`, который
строит провайдера против произвольного OpenAI-совместимого эндпоинта, целиком
через переменные окружения:

- `BRAID_TEST_OPENAI_BASE_URL` — базовый URL API. По умолчанию
  `http://localhost:11434/v1` (адрес Ollama), если переменная не задана.
- `BRAID_TEST_OPENAI_MODEL` — имя модели. Дефолта нет намеренно: какая модель
  доступна локально, заранее не угадать. Без неё перезапись пропускается с
  понятным сообщением.
- `BRAID_TEST_OPENAI_API_KEY` — опционально, локальным серверам обычно не
  нужен.

Наличие `BRAID_TEST_OPENAI_BASE_URL` — это и есть переключатель режима:
`setupAgent` (`internal/agent/agent_test.go`) передаёт VCR-рекордеру
`recorder.ModeRecordOnly`, чтобы перезаписать (а не пытаться воспроизвести и
провалиться на несовпадении) уже лежащую на диске протухшую кассету. Без этой
переменной рекордер работает в дефолтном режиме `ModeRecordOnce`
(replay, если кассета уже существует) — так работают все остальные тесты
пакета.

**Команда перезаписи**, когда эндпоинт появится:

```
BRAID_TEST_OPENAI_BASE_URL=http://localhost:11434/v1 \
BRAID_TEST_OPENAI_MODEL=<имя-модели> \
go test ./internal/agent/ -run TestCoderAgent -v
```

`TestCoderAgent` сейчас всё равно пропускается (`t.Skip`) при отсутствии
`BRAID_TEST_OPENAI_BASE_URL` — сообщение скипа само подсказывает эту команду.
Кассеты нужно будет перезаписывать заново при любом изменении схемы
инструментов (`internal/agent/tools/`) или системного промпта
(`internal/agent/templates/*.md.tpl`, `internal/agent/prompt/`) — записанные
тела запросов содержат их целиком, и любое расхождение снова ломает сравнение
VCR-матчера.

## Поведение, требующее проверки

### Провайдер теряет поля при записи токена — исправлено

`refreshOAuthTokenLocked` и `SetProviderAPIKey` писали на диск только
`providers.<id>.api_key`/`.oauth`; для провайдера вне встроенного каталога
это означало потерю `base_url`/`type`/`name` при следующей перезагрузке и
отбраковку как невалидного custom-провайдера (каталожный `copilot` не страдал
— его `configureProviders` восстанавливает из каталога независимо от файла).
Оба пути теперь пишут `type`/`base_url`/`name` вместе с кредами, но только
когда провайдера нет во встроенном каталоге (`ConfigStore.isCatalogProvider`)
— иначе в пользовательском файле зафиксировался бы каталожный `base_url` и
обновления каталога перестали бы доезжать. Заодно оба пути отказались от
полной перезагрузки конфига после записи (пишут через `update()`, а не
`SetConfigFields`), а `SetProviderAPIKey` теперь сначала валидирует
провайдера и только потом пишет на диск.

## Незавершённый ребрендинг

- В комментариях остались упоминания `Charm™` там, где они описывают
  происхождение поля или стиля (`internal/ui/logo/logo.go`,
  `internal/ui/styles/styles.go`). Это факты, а не оформление, поэтому не
  тронуты.
- ~~Буквы логотипа B, A, I, D нарисованы под ребрендинг и по стилю грубее
  оригинальных C, R, U, S, H.~~ Закрыто: `LetterB` и `LetterD` в
  `internal/ui/logo/letterforms.go` перерисованы в том же трёхстрочном
  полублочном стиле (`▀▄█` + пробел, stretch через `letterformProps`), что
  и `LetterC`/`LetterR`/`LetterU`. B получила настоящую сплошную
  перекладину (`███▄` во второй строке) вместо намёка на неё через
  чередование `▀`/`▄` — с прежним подходом буква не читалась в слове.
  D осталась замкнутой на каждом ярусе (шапка `▄`, стенка `█`), но нижняя
  строка — только `▀` (плюс пробелы), как у всех остальных букв: попытка
  скруглить подошву через `█`/`▄` опускала D ниже общей базовой линии и
  делала её визуально крупнее соседей. `LetterA` и `LetterI` уже были в
  этом стиле и не менялись.

## Ограничения перенесённых определений агентов

Решение пользователя (2026-08): Braid больше не сканирует чужие каталоги
конфигов сам. Discovery — `internal/config/agents_markdown.go` (`agentDirs`)
и `internal/config/load.go` (`GlobalSkillsDirs`, `projectSkillSubdirs`) —
читает только `.braid/agents` и `.braid/skills` (плюс их глобальные
эквиваленты и `options.skills_paths`). Раньше туда же попадали
`.claude/agents`, `.opencode/agent`, `.agents/skills`, `.claude/skills`,
`.cursor/skills`, `.opencode/skills` — то есть Braid молча доверял
содержимому каталогов, которые пишет другой инструмент, без валидации и без
уведомления пользователя о том, что не смогло примениться.

Перенос теперь идёт только через явный импорт — `braid import claude|opencode
[--skills] [--agents] [--dry-run] [--global] [--force]`
(`internal/config/import.go`, `internal/cmd/import.go`). Импорт копирует в
`.braid/skills`/`.braid/agents`, а не читает чужой каталог на лету, и на
каждый файл печатает отчёт (`imported`/`adjusted`/`skipped` + причина/
предупреждения) — те же ограничения ниже применяются, но теперь они видны
пользователю в момент импорта, а не выясняются постфактум по логам.

- Блоки `permission:` из файлов opencode **не применяются** ни при обычной
  загрузке, ни после импорта. Роль, запертая там в read-only, в Braid
  получит всё, что перечислено в её `tools`. Импорт репортит это как
  предупреждение («permission block is not supported; restrict tools via the
  tools list instead») и оставляет комментарий в frontmatter, но само поле
  не пишет. Ограничивать нужно списком `tools` или секцией `permissions`
  конфига.
- Поле `model` из чужих файлов понимает ссылки вида `provider/model-id`,
  если такая модель есть среди настроенных провайдеров — резолвится через
  `config.ResolveModelString`. Слотов `large`/`small` для `Agent.Model`
  больше не существует: эти слова не имеют особого смысла даже в
  собственных агент-файлах Braid и обрабатываются как любая другая
  нерезолвящаяся строка. Значения, которые ни на что не резолвятся
  (например, `opus` — имя модели из другого инструмента, которого нет в
  конфиге, или буквально `large`/`small`) при импорте не отбрасываются
  молча: поле `model` опускается (агент наследует основную модель), но
  исходное значение остаётся в frontmatter комментарием
  (`# original model: ... — not available`), и импорт репортит это как
  предупреждение вместо `slog.Debug`.
- `reasoning_effort`/opencode-шный `effort`: значения `low`/`medium`/`high`
  переносятся как есть; близкие, но нестандартные (`max`, `minimal`, ...)
  маппятся на ближайший валидный уровень с предупреждением; нераспознанные —
  отбрасываются с предупреждением и остаются комментарием в frontmatter.
- opencode-шные `temperature`/`top_p`: у `config.Agent` нет таких полей.
  Импорт не роняет файл и не выдумывает поле — значение остаётся
  комментарием в frontmatter, импорт репортит предупреждение.
- Имена инструментов, которым нет соответствия (например, `WebSearch`),
  при импорте не отбрасываются молча — репортятся как предупреждение с
  именем инструмента. При обычной загрузке `.braid/agents` трансляция имён
  Claude Code (`Read`→`view` и т.д., `ClaudeToolNames` в
  `agents_markdown.go`) больше не применяется вообще: файлы в собственном
  каталоге Braid должны уже называть инструменты по-своему. Транслятор не
  удалён — он используется только импортом.
- Делегирование одноуровневое: роль не может вызвать другую роль.
- Глобальный каталог opencode (`--global`) — предположение
  (`~/.config/opencode/{skills,agent}`), не проверенное против реальной
  установки: opencode не является зависимостью этого репозитория, сверить
  не с чем. Если оно разойдётся с реальным расположением, `braid import
  opencode --global` просто ничего не найдёт (штатно обрабатываемый случай
  отсутствующего каталога), а не упадёт.
