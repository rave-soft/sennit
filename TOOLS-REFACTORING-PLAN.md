## Цели

- Сократить лишние model turns и повторные вызовы инструментов.
- Устранить разрывы между `tool_call` и `tool_result` при переносе истории.
- Сделать схемы, разрешения, регистрацию и отображение инструментов согласованными.
- Улучшить наблюдаемость provider-запросов, retries и выполнения инструментов.
- Добавить безопасные специализированные инструменты для частых операций.

## Наблюдения по логам

1. После `Trimmed the carried sub-agent session` встречается
   `Dropping orphaned tool result with no matching tool call`. Текущий trimming
   может разорвать единый обмен `assistant(tool calls) + tool results`.
2. `ModelProvider called` записывается на каждый вызов callback, поэтому большое
   число таких строк нельзя интерпретировать как число реальных сетевых запросов.
3. Фиксированный бюджет переносимой истории в 120 000 символов не учитывает
   context window модели, system prompt, schemas инструментов, текущий запрос и
   резерв ответа.
4. Текущий `sennit_logs` не позволяет отфильтровать и связать события одного
   session/run без дополнительных вызовов поиска.

## P0: производительность, корректность истории и наблюдаемость

### T0. Параллельное выполнение read-only инструментов

**Где:** конструкторы `read`, `grep`, `ripgrep`, `glob`, `ls`, `sennit_logs` и
read-only LSP-инструментов.

- Заменить `fantasy.NewAgentTool` на `fantasy.NewParallelAgentTool` для чистых
  read-only операций.
- Оставить последовательными инструменты, которые меняют файлы, сессии,
  очереди, задачи и треды.
- Добавить тест классификации: каждый parallel tool действительно read-only и
  не меняет разделяемое состояние.
- Измерить wall-clock assistant-turn с несколькими независимыми чтениями до и
  после изменения.

**Критерий готовности:** независимые read-only calls из одного assistant-turn
исполняются конкурентно, при этом race-тесты и проверки состояния проходят.

### T1. Атомарный trimming tool-exchange

**Где:** `internal/agent/subagent_memory.go`, `internal/agent/compat.go`.

- Сдвигать точку разреза до ближайшей границы exchange: assistant-сообщение с
  tool calls и соответствующие tool results должны переноситься вместе.
- Непомещающийся exchange заменять детерминированной текстовой заглушкой без
  синхронного обращения к модели.
- Переписать doc-комментарий `trimToBudget`, который сейчас явно разрешает
  разрыв exchange и полагается на repair в `compat.go`.
- Добавить тесты для параллельных calls, частичного набора results и обрезки на
  границе exchange.

**Критерий готовности:** trimming не создаёт orphan results в интеграционном
тесте trim → prepare prompt. Общий счётчик repairs не обязан стать нулевым:
orphan'ы также возникают после прерванного стрима и ручной отмены.

### T2. Бюджет истории по текущей модели

**Где:** `internal/agent/subagent_memory.go`, runtime/model configuration.

Рассчитывать бюджет как:

```text
context window
- system prompt
- tool schemas
- current prompt
- output reserve
- safety margin
```

- Приводить результат tokenizer любого провайдера к единой консервативной
  шкале, чтобы одинаковая история имела воспроизводимый бюджет.
- Для провайдеров без tokenizer применять консервативную оценку.
- Учесть, что `carryOverMessages` вызывается до сборки runtime: либо перенести
  расчёт позже, либо использовать верхнюю оценку system prompt и tool schemas.
- Сначала сворачивать старые tool outputs и старые сессии в persistent summary.

**Критерий готовности:** переносимая история всегда укладывается в доступный
контекст с заданным резервом ответа.

### T3. Разделить runtime callback и provider request в логах

**Где:** `internal/agent/turn.go`, provider runtime.

- Перевести `ModelProvider called` в DEBUG.
- Отдельно логировать начало и окончание реального provider request.
- Добавить `session_id`, `run_id`, `turn_id`, `step`, `attempt`, `retry_reason`,
  latency, input/output tokens и cache hit.
- Различать normal tool continuation, retry, auth refresh, summarize и explicit
  continuation.

**Критерий готовности:** по одному `run_id` можно определить точное число
сетевых запросов и причины каждого дополнительного запроса.

### T4. Расширить диагностику orphan repair

**Где:** `internal/agent/compat.go`.

- Добавить к предупреждению session/message ID, источник истории и выполненное
  repair action.
- Различать persisted history, carried history, summary и interrupted stream.
- Добавить счётчик repairs по причинам.

**Критерий готовности:** остаточный orphan можно локализовать по одной записи
лога без ручного сопоставления нескольких потоков событий.

## P1: улучшение существующих инструментов

### T5. Расширить `sennit_logs`

**Где:** `internal/agent/tools/sennit_logs.go`.

После T3 выполнить сквозную нормализацию полей slog (`session_id`, `run_id`,
`component`) и только затем добавить параметры:

- `level`, `component`, `contains`;
- `session_id`, `run_id`;
- `since`, `limit`, `cursor`.

Пересмотреть текущий потолок в 100 строк, чтобы cursor не увеличивал число
вызовов на обычной диагностике. Возвращать число совпадений, признак усечения и
следующий cursor. Добавить режим коррелированной цепочки provider request → tool
call/result → trimming → repair. Баг переноса строк через границу 8 KB уже
исправлен и в объём задачи не входит.

### T6. Пагинация и метаданные `read`, `ripgrep`, `glob`, `ls`

**Где:** `internal/agent/tools/read.go`, `ripgrep.go`, `grep.go`, `glob.go`,
`ls.go`.

- `read`: сохранить существующие `offset`/`limit`, добавить `total_lines`,
  структурный `next_offset` и stable continuation token.
- `ripgrep`: добавить `max_results`, `before_context`, `after_context`, cursor и
  сортировку по path или mtime.
- `glob`: добавить настраиваемый `max_results` и cursor; стабильная сортировка и
  metadata об усечении уже существуют.
- `ls`: добавить cursor; metadata об усечении уже существуют.
- Унифицировать формат результата grep/ripgrep, не объединяя семантику Go и
  Rust regex.

**Критерий готовности:** модель может продолжить усечённую выдачу без повторного
поиска и без вычисления следующего offset вручную.

### T7. Полная JSON Schema MCP-инструментов

**Где:** `internal/agent/tools/mcp-tools.go`.

Не сводить MCP `inputSchema` только к `properties` и `required`. Вложенные
ограничения уже сохраняются внутри properties; необходимо сохранить корневые:

- `additionalProperties`;
- `oneOf`, `anyOf`, `allOf`;
- `$defs` и ссылки;
- root description и defaults.

Если Fantasy не принимает полную schema, расширить boundary API вместо lossy
преобразования. Первый обязательный contract-тест: свойство с `$ref` на
корневой `$defs`; затем root `oneOf` и `additionalProperties: false`.

### T8. Единый `ToolDescriptor`

**Где:** новый leaf-пакет `internal/toolmeta`,
`internal/agent/tool_registry.go`, `internal/config/toolnames.go`, permission
policy, UI tool renderers и документация. Leaf-пакет необходим, чтобы не создать
цикл импортов между `config` и `agent/tools`.

Предлагаемые поля:

```text
name, aliases, builder, gate, default_enabled,
access_mode, writes, confined, parallel_safe,
schema, renderer_class, docs_category
```

`access_mode` должен поддерживать статический read-only/write и динамическое
решение самого инструмента, необходимое для `bash`. Из descriptor генерировать
список имён, default set, permission classification, UI-классификацию и reference
table. Dynamic MCP/custom-agent tools оставить отдельными descriptor providers.
Существующий `toolSpecs()` остаётся основой регистрации; миграция gate'ов должна
иметь тест полного совпадения старого и нового разрешённого набора.

**Критерий готовности:** метаданные встроенного инструмента задаются в одном
месте; тест автоматически обнаруживает drift схемы, permissions, gate и UI.

### T9. Schema-contract тесты для всех инструментов

- Проверять уникальность имён.
- Сверять required-поля схемы с runtime validation.
- Задавать `enum`, `minimum`, `maximum`, `minLength` в schema, а не только prose.
- Проверять валидные примеры и отклонение неверных enum/range до handler.
- Проверять стабильность схем между провайдерами.

**Критерий готовности:** невалидные параметры не требуют дополнительного model
turn для исправления ошибки handler.

### T10. Проверить инвалидации существующего runtime cache

**Где:** `internal/agent/runtime_cache.go`, `internal/agent/coordinator.go`.

Runtime уже кэшируется по версиям config, MCP и local state, а подагенты
строятся внутри кэшированной сборки. Сначала измерить число инвалидаций
`runtimeKey` за сессию. Если оно мало, ограничиться исправлением устаревшего
комментария `buildAgent`. Если велико, устранить источник лишних вызовов
`invalidateRuntime`, не добавляя второй кэш.

**Критерий готовности:** комментарии соответствуют текущей архитектуре, а
частота инвалидаций измерена и не вызывает повторных сборок без изменения
эффективной конфигурации.

## P2: новые инструменты

### T11. `multi_read`

Рассматривать только после T0 и замера числа read calls. Читает список
диапазонов файлов за один вызов с общим byte/token budget, per-file ошибками,
metadata и продолжением усечённых секций. Реализовать поверх существующего
`read`, сохранив confinement, permissions и file tracker.

### T12. `git_status`, `git_diff`, `git_log`

Отложенные read-only инструменты со структурированным результатом. Безопасность
уже обеспечивается `bash`: `git status`, `git diff` и `git log` входят в
`safeCommands`. Реализовывать только если замеры подтвердят пользу структуры и
лимитов вывода:

- фильтр путей;
- staged/unstaged;
- stat или patch;
- лимит patch/output;
- защита `-C` и путей вне worktree на уровне существующего confinement.

### T13. `lsp_hover`, `lsp_workspace_symbols`

- Сначала `lsp_workspace_symbols`: ranked search по query, kind, path и limit.
- Затем `lsp_hover`: тип, сигнатура и документация; принимать имя символа либо
  файл/позицию, чтобы не требовать предварительного grep.

Проверить server capabilities при initialize. Оба инструмента должны учитывать
worktree working directory и возвращать понятную ошибку, если подходящий LSP не
запущен.

### T14. `agent_trace`

Диагностический read-only инструмент по `session_id` или `run_id`. Реализовать
строго после сквозной простановки структурированных полей из T3 и индексации из
T5:

- provider attempts и retry reasons;
- token usage и cache hits;
- summarize/trimming events;
- tool call/result pairing;
- continuation и auth refresh.

По умолчанию не возвращать prompts, tool arguments, secrets и полный tool
output.

### T15. `repo_map`

Рассматривать только после замера числа вызовов на первичное изучение
репозитория. При подтверждённой пользе возвращать компактную карту: языки,
модули, manifests, ключевые директории, symbol outline, git status и размеры
крупных файлов. Не включать содержимое файлов без явного запроса.

1. **Итерация 0:** T0; исправить устаревшие doc-комментарии `buildAgent` и

2. **Итерация 1:** T3 с нормализацией slog-полей → T4 → минимальный T1 без

## Исходный аудит плана (2026-08-24)

Ниже — результат сверки первоначальной версии каждого пункта с текущим кодом.
Часть исходных утверждений была неактуальна, часть переоценивала или
недооценивала объём работы, и была найдена оптимизация дешевле всего блока P2.

### Главное: read-only инструменты выполняются последовательно

Не отмечено в плане, но по эффекту перекрывает T11 и половину T6.
`read`, `grep`, `ripgrep`, `glob`, `ls`, `sennit_logs`, `lsp_symbols`,
`lsp_definition` созданы через `fantasy.NewAgentTool`
(`internal/agent/tools/read.go:98`, `grep.go:123`, `ripgrep.go:57`,
`glob.go:54`, `ls.go:75`, `sennit_logs.go:79`, `lsp_symbols.go:25`,
`lsp_definition.go:35`), то есть `parallel: false`
(`fantasy/tool.go:102-115`). В диспетчере fantasy
(`agent.go:1666-1700`) непараллельный tool исполняется **прямо в теле
координирующей горутины** под `sequentialMu`: пять `read` в одном assistant-turn
идут строго друг за другом и вдобавок задерживают отправку следующих
параллельных вызовов из той же пачки.

Замена на `NewParallelAgentTool` для чистых read-only инструментов — это
несколько строк, ноль изменений в схемах и промптах, и она даёт ровно ту
экономию wall-clock, ради которой в P2 предлагается `multi_read`. Делать это
надо до T11, а не после: если параллельность включена, `multi_read` экономит
только токены на дублирующихся заголовках вызовов, и его приоритет падает.
Осторожно с `bash`, `edit`, `write`, `multiedit`, `todos`, `thread_*`,
`task_*` — там последовательность защищает состояние.

### T1 — премисса верна, критерий готовности неверен

`trimToBudget` (`internal/agent/subagent_memory.go:139`) действительно режет по
границам сообщений, а не exchange, и может отделить `tool_result` от его
`tool_call`. Но:

1. Предупреждение `Dropping orphaned tool result` — это **штатный
   ремонтный путь**, а не признак поломки (`compat.go:141`), и рядом с ним
   работает `syntheticToolResultsForOrphanedCalls` (`compat.go:171`),
   закрывающий обратный случай. Orphan'ы возникают ещё и из прерванного
   стрима и из ручной отмены — то есть после T1 предупреждение всё равно
   останется в живых логах. Критерий «предупреждение не появляется» годится
   только для узкого интеграционного теста trim → preparePrompt; в общем
   виде он недостижим и его не надо ставить как цель.
2. Заявленный сейчас в коде контракт — «резать можно где угодно, compat.go
   починит» — записан в doc-комментарии `trimToBudget`. Если T1 меняет
   контракт, комментарий надо переписать, иначе следующий читатель решит,
   что атомарность необязательна.
3. Пункт «большой блок заменять компактным summary» — это синхронный вызов
   модели внутри `carryOverMessages`, то есть на горячем пути делегации, с
   собственной ценой, задержкой и режимом отказа. Это отдельная задача, а не
   буллет внутри T1. Минимальная безопасная версия: не разрывать exchange, а
   не влезающий exchange заменять текстовой заглушкой без модели.

Реальный объём T1 — примерно «сдвинуть точку разреза до ближайшей границы
exchange» в `trimToBudget`, около десятка строк плюс тесты. Так и стоит его
описать.

### T2 — правильная цель, недооценённая цена

`maxCarriedSubAgentChars` (`subagent_memory.go:21`) действительно фиксирован, и
его doc-комментарий честно объясняет, почему он в символах: бюджет должен
работать для провайдеров без токенайзера. Возражение к плану одно: «использовать
tokenizer провайдера, если доступен» вводит бюджет, который на разных
провайдерах даёт разный результат для одной и той же истории, — и тогда падение
воспроизводится только на одном провайдере. Нужно явно решить и записать:
токенайзер считает, но результат приводится к одной консервативной шкале.

Вход в формулу тоже неполон: `carryOverMessages` вызывается до сборки runtime,
и на этот момент неизвестны ни финальные tool schemas, ни system prompt (они
собираются в `runtimeFor`, `coordinator.go:1202`). Либо бюджет считается позже,
либо в формулу закладывается верхняя оценка.

### T3 — согласен, с уточнением

`slog.Info("ModelProvider called", …)` (`turn.go:442`) действительно шумит.
Но утверждение «это не число сетевых запросов» стоит уточнить: callback
вызывается по одному разу на попытку стрима, то есть это довольно близкая
верхняя оценка, а не произвольное число. Настоящая проблема — что строка не
несёт ни `session_id`, ни `run_id`, ни причины, а retry логируется отдельно
(`turn.go:420`, `providerRetryLogFields` в `compat.go`) и не связан с ней.

Перед добавлением полей стоит зафиксировать словарь: в коде уже сосуществуют
`session_id` и `session`, `component` есть ровно в одном месте
(`agent.go:1107`). Без нормализации фильтры из T5 работать не будут.

### T4 — согласен, объём маленький

Возражений нет. Учесть, что `filterOrphanedToolResults` не знает происхождения
истории — «carried / persisted / interrupted» придётся протаскивать в
`preparePrompt` параметром, иначе различить источники нечем.

### T5 — один пункт уже сделан, один зависит от T3

- «Исправить потерю записей, пересекающих границу 8 KB чанка» — **уже
  исправлено** в `9a8dba2a`; в `readLastLines` (`sennit_logs.go:120-190`) стоит
  и исправленный перенос `remainder`, и комментарий, описывающий старый баг.
  Пункт надо убрать из плана, иначе он будет переоткрыт.
- Фильтры `session_id` / `run_id` бесполезны, пока эти поля не проставлены в
  логах повсеместно (сейчас — точечно). T5 в этой части не «после T3», а
  «после T3 плюс сквозной проход по slog-вызовам»; это стоит назвать отдельной
  подзадачей, иначе объём T5 занижен вдвое.
- `lines` сейчас ограничен `maxLogLines = 100` (`sennit_logs.go:48`). Cursor
  без пересмотра этого потолка даст модели пагинацию по 100 строк на вызов, то
  есть больше вызовов, а не меньше — ровно против цели плана.

### T6 — примерно половина уже есть

- `read` уже имеет `offset` и `limit` и уже сообщает о продолжении
  (`read.go:48-49`, `read.go:249`). Из списка реально отсутствуют `total_lines`
  и структурный `next_offset`; `end_line` дублирует `limit` и создаёт два
  способа сказать одно и то же — лучше не добавлять.
- `glob` уже возвращает `truncated` и `number_of_files` и имеет стабильную
  сортировку (`glob.go:39-95`, `runRipgrep` сортирует `sort.SliceStable`).
  Отсутствует только параметр `max_results` — лимит зашит числом 100
  (`glob.go:74`).
- `ls` уже возвращает `truncated` и `number_of_files` (`ls.go:47-48`).
- Реально пустые места: `ripgrep` без `max_results` и контекста строк
  (`ripgrep.go:23-27`) и отсутствие cursor'ов везде.

Пункт «унифицировать контракт grep/ripgrep» стоит уточнить: это два разных
инструмента с разным синтаксисом регулярок (Go regexp против Rust regex).
Унифицировать можно формат результата, но не семантику паттерна — иначе
получится инструмент, который на одном бэкенде принимает то, что на другом
падает.

### T7 — верно по сути, но список потерь шире, чем есть

`Info()` (`mcp-tools.go:81-105`) действительно берёт только `properties` и
`required`. Но значения внутри `properties` передаются целиком, поэтому
«ограничения массивов и строк», enum'ы, вложенные объекты и defaults **внутри
свойств не теряются**. Теряются именно корневые ключи: `additionalProperties`,
корневые `oneOf`/`anyOf`/`allOf`, `$defs` и описание корня.

Практически опасен из этого списка один случай: `$ref` внутри свойства,
указывающий на выброшенный `$defs`, — схема остаётся синтаксически валидной,
но ссылка висит в пустоту. Этот случай стоит вынести в отдельный тест первым.

### T8 — есть блокер импортов и есть уже существующая часть

- Реестр регистрации **уже централизован**: `toolSpecs()`
  (`internal/agent/tool_registry.go:70`) — таблица с `Gate`/`Build`, и есть
  пиннинг-тест `TestBuildToolsPinnedSet`, а также
  `tools/permission_coverage_test.go`. То есть «регистрируется в одном месте»
  наполовину выполнено; T8 — это про метаданные, а не про регистрацию.
- Блокер: `internal/agent/tools` импортирует `internal/config` (об этом прямо
  написано в `toolnames.go:19-21` — обратный импорт даст цикл). Значит
  единый `ToolDescriptor` **не может** жить ни в `config`, ни в
  `agent/tools`. Нужен отдельный leaf-пакет (например `internal/toolmeta`),
  и это надо записать в плане, иначе реализация упрётся в цикл на первом же
  коммите.
- Поле `read_only` как булев флаг не выражает то, что делает `bash`: там
  read-only определяется разбором самой команды (`bash.go:237-249` плюс
  `safe.go`). Descriptor должен допускать «решает сам инструмент», иначе
  классификация станет тише и грубее, чем сейчас.
- `Gate` в таблице — граница того, что модели вообще разрешено; в комментарии
  к `toolSpec` это названо регрессией безопасности, а не стиля. Любая
  генерация gate'ов из descriptor'а должна сопровождаться тестом на
  посимвольное совпадение старого и нового набора.

### T9 — согласен, добавить одно

Стоит включить проверку, что имя инструмента и его `allToolNames()`
(`config/toolnames.go:99`) не разъезжаются, и что `CanonicalToolName`
покрывает все переименования, — сейчас это соответствие держится только
комментарием в `config/import.go:516`.

### T10 — премисса устарела

Кэш runtime **уже существует**: `internal/agent/runtime_cache.go`, ключ
`runtimeKey{config, mcp, local}`, с single-flight и проверкой актуальности
ключа после сборки. Подагенты строятся внутри `buildTools`, то есть внутри
сборки этого runtime, — значит повторная делегация **не** пересобирает ни
prompt, ни schemas, ни MCP readiness, пока не изменилась одна из версий.
Отдельно `buildCustomAgentTool` (`custom_agent_tool.go:86-105`) уже
пересобирает делегата только при реальном изменении определения агента.

Doc-комментарий в `buildAgent` (`coordinator.go:664`), утверждающий, что
подагенты пересобираются на каждый `coordinator.Run`, относится к состоянию до
кэша и сейчас вводит в заблуждение — его надо поправить, и это, возможно, весь
T10.

Прежде чем делать T10 в заявленном виде, нужно измерить: сколько раз реально
инвалидируется `runtimeKey` за сессию. Если ответ «редко», пункт закрывается
правкой комментария; если «часто» — чинить надо источник инвалидации
(`invalidateRuntime`, `coordinator.go:1195`), а не добавлять второй кэш.

### T11 — понизить приоритет

См. раздел про параллельность выше. После включения `NewParallelAgentTool` для
read-only инструментов `multi_read` даёт только экономию на оверхеде вызовов.
Если делать, то поверх `read` — как и написано, — но решение принимать по
замеру после параллелизации, а не до.

### T12 — заявленная выгода уже получена

«Безопасная классификация без общего shell permission prompt» уже работает:
`git status`, `git diff`, `git log` входят в `safeCommands`
(`internal/agent/tools/safe.go:50,59`), и `bash` пропускает их без запроса
разрешения (`bash.go:237-249`); `confinement.go:111` отдельно разрешает
`git diff/log/show`. Остаётся только структурированный вывод — это заметно
более слабое обоснование, чем в плане. Плюс новые инструменты придётся
отдельно защищать от `-C <path>` и от путей вне worktree, что `bash` уже
умеет. Рекомендация: либо переформулировать обоснование через структурированный
вывод и лимит патча, либо отложить.

### T13 — премисса верна, но UX-цена не учтена

`lsp_hover` и workspace symbols действительно отсутствуют: в
`internal/lsp/client.go` есть `Definition`, `FindReferences`,
`DocumentSymbols`, но ни hover, ни `workspace/symbol`. `lsp_symbols` работает
только по одному файлу (`lsp_symbols.go:16`). То есть пункт настоящий.

Замечание: существующие LSP-инструменты требуют `line`/`character`, а модель
позицию символа обычно не знает и вынуждена сначала делать `grep` — то есть
`lsp_hover` в позиционном виде **добавит** лишний вызов вместо того, чтобы
убрать. Полезнее сначала сделать `lsp_workspace_symbols` (поиск по имени) и
разрешить `lsp_hover` принимать имя символа, а не только позицию. Также нужно
проверить, объявляются ли соответствующие capabilities при initialize.

### T14 — зависимость важнее содержания

`agent_trace` целиком стоит на структурированных полях из T3 и на индексе из
T5. Пока `run_id` не проставлен сквозняком, инструмент выдаст пустой ответ на
большинство запросов, что хуже, чем его отсутствие. Держать T14 строго после
того, как метрика «по одному run_id видно число запросов» из T3 реально
выполняется, — иначе это отладочный инструмент, который сам требует отладки.

### T15 — единственный пункт без опоры на измерение

`repo_map` описан через содержимое, а не через задачу, которую он сокращает.
Прежде чем делать, нужно из метрик (последний раздел плана) получить, сколько
вызовов сейчас уходит на «изучить репозиторий»; иначе есть риск получить
третий способ делать то, что уже делают `glob` + `ls` + `read`.

### Порядок реализации

Предлагаемая правка:

1. **Итерация 0 (новая, самая дешёвая):** параллельность read-only
   инструментов; удалить из T5 уже сделанный пункт про 8 KB; поправить
   устаревшие doc-комментарии в `buildAgent` и `trimToBudget`.
2. **Итерация 1:** T3 (включая нормализацию имён полей) → T4 → T1 в
   минимальном виде (граница exchange без summary).
3. **Итерация 2:** T5 (после сквозной простановки `run_id`), T6 в
   сокращённом объёме, T7 начиная с `$defs`/`$ref`.
4. **Итерация 3:** T9, затем T8 с leaf-пакетом под descriptor; T10 —
   только после замера инвалидаций.
5. **Итерация 4:** T13 (сначала workspace symbols), T14, далее T11/T12/T15
   по измеренной частоте.

### Метрики

К списку стоит добавить две, без которых половина решений выше не проверяема:

- доля tool-вызовов, выполненных параллельно, и wall-clock одного
  assistant-turn с несколькими read-only вызовами;
- число инвалидаций `runtimeKey` за сессию (проверка премиссы T10).

И убрать «cache hit rate runtime подагентов» как отдельную метрику: у
подагентов нет своего кэша, они попадают в кэш основного runtime, так что это
та же метрика, что и предыдущая.
