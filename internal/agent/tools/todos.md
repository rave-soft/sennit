Manage a structured task list for multi-step work; each task has pending/in_progress/completed state. Always send the FULL list including completed tasks (marked completed, never dropped), so finished work stays visible. Omitting a completed item does not retract it: outside a new cycle it is appended back (see below), and the only way to clear the list is to send an entirely new one. When working sequentially, keep one task in_progress at a time. Once every task in the list is completed that list is finished: start the next piece of work with a FRESH list containing only the new tasks, never by appending them to the completed one. When tasks run in parallel — delegated to threads or subagents — mark EVERY currently-running task in_progress and complete each one individually as its worker finishes, so the task list reflects real concurrent progress. Skip for simple or single-step tasks.

A call does not always replace the stored list exactly as sent — two automatic adjustments happen server-side:
- If the previous list was fully completed and this call's list is entirely completed items too, that's read as this call still trailing the finished cycle, not starting a new one: any of those items whose content matches something the previous list already had is dropped rather than reopening the closed list. Starting a new cycle means including at least one pending or in_progress item.
- Outside a new cycle, a previously completed item this call's list doesn't mention is appended back rather than dropped — a small/local model does not always resend every already-completed item, and treating the call as a strict replacement would silently erase those. An item this call does mention, at any status, is taken as given and never merged over.
