# Пайплайн разработки

Используй этот процесс, когда пользователь просит реализовать изменение через пайплайн разработки.

## Подготовка

1. Зафиксируй исходную задачу пользователя дословно или достаточно полно, критерии приемки и состояние рабочего дерева.
2. Не включай в работу изменения, существовавшие до запуска пайплайна, если они не относятся к задаче.
3. Считай каждый вызов developer или reviewer новым stateless session: субагент не помнит предыдущие вызовы, их prompts и результаты. Нельзя передавать контекст ссылками вроде «см. выше», «исправь блоки» или «продолжи предыдущую работу» без полного содержимого handoff.
4. Каждый вызов developer и reviewer должен быть полностью самодостаточным и содержать handoff по шаблону ниже. Это обязательно и для первого вызова, и для каждого повторного раунда после `FAIL`.
5. В каждом handoff явно потребуй перечитать фактическое состояние репозитория и current diff перед действиями; summary diff не заменяет проверку фактического diff.
6. Основной агент координирует процесс и не реализует задачу вместо субагентов.
7. Всегда начинай каждую отдельную задачу с `middle-developer`. После трех `FAIL` middle-этапа переходи к `senior-developer`.
8. Каждый этап состоит максимум из трех последовательных раундов разработки и ревью. Первичная реализация и первое ревью считаются первым раундом.
9. При успешном ревью и финальной проверке заверши текущую задачу и сбрось все счетчики раундов и этапов. Любую следующую задачу, включая следующую задачу того же пользовательского запроса, снова передавай `middle-developer` с первого раунда.

## Обязательный handoff для каждого вызова

Передай developer или reviewer одно сообщение, включающее все разделы ниже. Не удаляй разделы на повторных раундах; если значение отсутствует, напиши `нет`.

```text
ROLE: <middle-developer|senior-developer|reviewer>
TASK: <краткое имя задачи>
ORIGINAL USER REQUEST:
<полный исходный запрос пользователя, включая ограничения>

CURRENT STAGE AND ROUND:
<этап, номер раунда из 3, причина запуска/повторного запуска>
ACCEPTANCE CRITERIA:
<полный текущий список требований и проверяемых критериев приемки>

PREVIOUS ROUNDS:
<для каждого завершённого раунда: developer/reviewer, статус PASS или FAIL,
что было изменено, какие проверки выполнены и какие замечания закрыты>
UNRESOLVED REVIEW FEEDBACK:
<полный текст всех актуальных блокирующих замечаний; не пересказывай их как
«исправь замечания». Для reviewer укажи также, какие старые замечания уже закрыты>

RELEVANT FILES:
<полный список файлов, относящихся к задаче, и назначение каждого>
CURRENT DIFF INSTRUCTION:
<проверь git status, затем фактические staged и unstaged diff; не доверяй
только этому описанию. Не изменяй файлы вне списка без явного обоснования>
BASELINE / PRE-EXISTING CHANGES:
<изменения, существовавшие до пайплайна, которые нельзя включать, либо «нет»>

REQUIRED CHECKS:
<релевантные узкие тесты, затем форматирование/lint/typecheck при наличии;
укажи уже выполненные проверки и их фактический результат>

INSTRUCTIONS:
<для developer: реализуй/исправь требования, не создавай коммит, запусти проверки
и сообщи изменённые файлы и результаты. Для reviewer: сначала перечитай фактический
current diff и тесты, затем проверь каждый критерий и выдай явный итоговый PASS или
FAIL. При FAIL перечисли полный список блокирующих замечаний, файл/место,
обоснование и конкретный ожидаемый результат; не ограничивайся общими словами.>
```

Для reviewer включай тот же полный контекст, включая исходный запрос, acceptance criteria, предыдущие раунды, все unresolved feedback, релевантные файлы, baseline, current diff instruction и проверки. Reviewer не должен полагаться на память developer или предыдущего reviewer. После reviewer `FAIL` передавай тому же разработчику новый полный handoff, а не только текст замечаний.

## Этап middle-разработчика

1. Передай задачу субагенту `middle-developer` с полным handoff.
2. После его работы вызови отдельного `reviewer` с полным handoff по тому же шаблону.
3. При `FAIL` передай все блокирующие замечания тому же `middle-developer` в полном handoff, затем снова вызови reviewer с полным handoff.
4. Выполни не более трех раундов разработки и ревью результата middle-разработчика.
5. При `PASS` перейди к финальной проверке. Если третье ревью завершилось `FAIL`, перейди к этапу senior-разработчика.

## Этап senior-разработчика

1. Этот этап начинается только после третьего `FAIL` middle-этапа. `senior-developer` разрабатывает сложное решение вместо не справившихся разработчиков и не выполняет ревью.
2. Передай `senior-developer` полный handoff: исходную задачу, критерии приемки, текущий фактический diff и все нерешенные замечания middle-этапа.
3. После его работы вызови отдельного `reviewer` с полным handoff.
4. При `FAIL` передай все блокирующие замечания тому же `senior-developer` в полном handoff, затем снова вызови reviewer с полным handoff.
5. Выполни не более трех раундов разработки и ревью результата senior-разработчика.
6. При `PASS` перейди к финальной проверке. Если третье ревью завершилось `FAIL`, остановись без коммита. Сообщи пользователю нерешенные замечания, выполненные проверки и текущее состояние изменений.

## Финальная проверка и коммит

1. После `PASS` самостоятельно проверь, что все требования выполнены, а рабочее дерево не содержит несвязанных изменений для коммита.
2. Запусти наиболее релевантные тесты, затем доступные форматирование, линтер или проверку типов, предусмотренные проектом.
3. Если финальная проверка выявила дефект, считай ее дополнительным `FAIL` текущего этапа: верни замечания текущему разработчику через полный stateless handoff, если лимит трех раундов еще не исчерпан. Иначе эскалируй с middle на senior или остановись после исчерпания senior-этапа.
4. Коммить только после успешного ревью и успешной финальной проверки.
5. Перед коммитом соблюдай обязательную процедуру создания коммита Braid: одновременно проверь `git status`, staged и unstaged diff и стиль последних коммитов; добавь только относящиеся к задаче файлы; проверь staged diff на секреты; составь semantic commit с требуемой атрибуцией; после коммита проверь `git status`.
6. Не отправляй коммит в удаленный репозиторий.

## Инварианты

- Всегда соблюдай порядок этапов: `middle-developer`, `senior-developer`.
- Максимум три раунда разработки и ревью на каждом этапе, всего не более шести раундов.
- Каждый developer и reviewer получает полный handoff и рассматривается как новый stateless session.
- Ревью выполняет только `reviewer`; разработчики только разрабатывают и исправляют свои решения по замечаниям.
- Следующий разработчик не подключается, если текущий этап получил `PASS`.
- Счетчики принадлежат только текущей задаче и не переносятся между задачами.
- После принятия задачи следующая задача всегда начинается с первого раунда `middle-developer`, независимо от того, какой разработчик завершил предыдущую.
- Разработчики не создают коммиты.
- Основной агент создает ровно один итоговый коммит только для принятой задачи.
- Не засчитывай ответ без явного `PASS` как успешное ревью.
- Не коммить при незавершенных тестах, блокирующих замечаниях или исчерпанном лимите senior-этапа.
