# План: мульти-аккаунтность провайдеров, прокси и ротация по лимитам

Статус: черновик плана разработки. Код ещё не написан.

## 1. Что нужно получить

1. К одному провайдеру (в первую очередь `codex`) можно подключить несколько
   учёток и переключаться между ними.
2. Отдельный интерфейс управления учётками провайдера: список, добавить,
   удалить, переименовать, сделать активной.
3. Прокси настраивается на двух уровнях: общий для провайдера и
   индивидуальный для каждой учётки (учётка перебивает провайдера).
4. В диалоге учёток видны текущие лимиты — там, где провайдер их вообще
   отдаёт (Codex отдаёт, остальные — нет).
5. Автоматическая ротация активной учётки на следующую пригодную. Триггер
   зависит от провайдера: у тех, кто сообщает остаток лимита (Codex) — при
   достижении настраиваемого нижнего порога; у остальных (opencode и прочие
   api-key) — по ответу 429, и настройки порога у них нет вовсе.

## 3. Принятые решения

Решения подтверждены пользователем.

| # | Решение | Пересмотр |
| --- | --- | --- |
| Р1 | Общий механизм `accounts[]` для любого провайдера, включая api-key-провайдеров (несколько ключей у Copilot/OpenAI/кастомных). Лимиты и ротация — capability: их реализует только Codex, остальные дают переключение и прокси | Сузить до Codex = не регистрировать остальных в реестре, формат конфига не меняется |
| Р2 | Учётки хранятся в отдельном файле `accounts.json` рядом с global-конфигом (`config.GlobalDBDir()`), права `0600`; в `sennit.json` остаётся только `providers.<id>.account` — id активной учётки | Переезд в `sennit.json` = сменить бэкенд `accounts.Store`, API не меняется |
| Р3 | Ротация — **между** запросами, текущий стрим не рвём | Ретрай на 429 добавляется поверх, отдельной фазой |
| Р4 | Когда исчерпаны все — запрос не отправляется, ошибка «все учётки исчерпаны до HH:MM» с указанием ближайшего `ResetsAt` | Мягкое поведение (продолжать на наименее исчерпанной) = один `if` в `Rotator.Pick` |
| Р5 | Минимальный лимит настраивается **только у провайдеров, которые сообщают остаток**. Порог — «остаток в процентах», по умолчанию 10 (`used_percent >= 90` → ротация). У провайдеров без лимитов (opencode и прочие api-key) настройки порога нет вовсе — ни в конфиге, ни в UI | — |
| Р6 | Проверяются **оба** окна (primary/secondary); учётка считается исчерпанной, если хоть одно окно за порогом | — |
| Р7 | Триггер ротации у провайдеров без лимитов — ответ **429**: учётка помечается остывающей (по `Retry-After`, иначе на дефолтный cooldown), запрос повторяется на следующей учётке | Отключается флагом `rotation.enabled` на провайдере |

## 4. Формат конфигурации

`~/.config/sennit/sennit.json` (глобальный скоуп):

```jsonc
{
  "providers": {
    "codex": {
      "proxy_url": "http://127.0.0.1:8080",   // общий прокси провайдера
      "account": "acc_personal",              // id активной учётки
      "rotation": {
        "enabled": true,
        "min_remaining_percent": 10,          // только у провайдеров с лимитами (Р5)
        "order": ["acc_personal", "acc_work"] // порядок обхода; пусто = порядок добавления
      }
    },
    "opencode": {
      "account": "acc_key_a",
      "rotation": {
        "enabled": true,                      // триггер — 429, порога тут нет (Р7)
        "cooldown": "10m",                    // если ответ не принёс Retry-After
        "order": ["acc_key_a", "acc_key_b"]
      }
    }
  }
}
```

`min_remaining_percent` у провайдера без capability `Usage` — ошибка
валидации конфига с внятным текстом («провайдер opencode не сообщает остаток
лимита; ротация для него срабатывает по 429»), а не молча игнорируемое поле.
Симметрично `cooldown` бессмысленен там, где есть настоящие окна лимита, и
тоже отвергается.

`~/.config/sennit/accounts.json` (0600, не коммитится, не редактируется руками):

```jsonc
{
  "version": 1,
  "accounts": {
    "codex": [
      {
        "id": "acc_personal",                 // стабильный, генерится при добавлении
        "label": "Личный Plus",               // редактируемое имя для UI
        "account_id": "user-abc…",            // chatgpt-account-id из JWT
        "email": "…",                         // если есть в id_token, только для показа
        "proxy_url": "",                      // "" = наследовать провайдерский; "none" = прямое
        "oauth": { "access_token": "…", "refresh_token": "…", "expires_at": 0 },
        "disabled": false,
        "usage": {                            // последний известный снимок лимитов
          "plan": "plus",
          "primary": { "used_percent": 42, "window_minutes": 10080, "resets_at": 0 },
          "secondary": { "used_percent": 7, "window_minutes": 300, "resets_at": 0 },
          "captured_at": 0
        }
      }
    ],
    "openai": [
      {
        "id": "acc_work_key",
        "label": "Рабочий ключ",
        "api_key": "sk-…",                    // альтернатива oauth для api-key провайдеров
        "proxy_url": "none"
      }
    ]
  }
}
```

Учётка держит либо `oauth`, либо `api_key` — по тому, чем аутентифицируется
провайдер. Для api-key-провайдеров блок `usage` отсутствует: лимитов они не
сообщают, и ротация для них выключена (см. реестр в §5.1).

`usage` пишется на диск специально: заголовки лимитов приходят только с
ответом, а диалог учёток должен что-то показывать сразу после открытия, до
первого запроса каждой из учёток.

### Миграция

Существующий `providers.codex` с `oauth`/`api_key` и без `account` при первом
запуске превращается в одну учётку: `id` = `acc_<account_id>` (или
`acc_default`), `label` = email или «Основная», `proxy_url` = текущий
`providers.codex.proxy_url`. Поля `oauth`/`api_key` в `sennit.json` остаются на
месте — они и есть проекция активной учётки (см. §5.2), поэтому откат на
старую версию бинарника продолжает работать. Миграция идемпотентна и
выполняется один раз при загрузке конфига.

## 5. Архитектура

### 5.1 Новый пакет `internal/providers/accounts`

Лист-пакет, не импортирует `config` (иначе цикл, как уже было с `proxyhttp`).

```go
type Account struct {
    ID, Label, AccountID, Email string
    ProxyURL string
    Token    *oauth.Token  // OAuth-провайдеры
    APIKey   string        // api-key-провайдеры; ровно одно из двух непусто
    Disabled bool
    Usage    Usage         // последний снимок; пуст для провайдеров без лимитов
}

type Store interface {
    List(providerID string) ([]Account, error)
    Get(providerID, accountID string) (Account, bool)
    Upsert(providerID string, a Account) error
    Remove(providerID, accountID string) error
    RecordUsage(providerID, accountID string, u Usage) error
}
```

Файловый бэкенд: чтение целиком, запись атомарная (`tmp` + `rename`) под
`lock.File` — тем же механизмом, что и refresh-лок в
`internal/config/credentials`, чтобы два процесса Sennit не затирали друг
друга.

**Реестр возможностей.** Мультиаккаунт включён для всех провайдеров, но
лимиты и ротация есть не у всех:

```go
type RotateOn int

const (
    RotateNever     RotateOn = iota // ротация не предлагается
    RotateThreshold                 // по остатку лимита, порог настраивается
    RotateRateLimit                 // по ответу 429, порога нет
)

type Capabilities struct {
    Usage    bool     // провайдер сообщает остаток лимита
    RotateOn RotateOn
    AuthKind AuthKind // OAuth | APIKey — определяет форму «Добавить учётку»
}

func CapabilitiesOf(providerID string) Capabilities
```

`Usage` + `RotateThreshold` истинны сейчас только для `codex`. Все остальные
получают `RotateRateLimit`: список учёток, переключение, прокси, форма ввода
ключа и переключение по 429 — но без цифр лимита и без поля порога.
Добавление нового провайдера с лимитами = одна запись в реестре плюс парсер
его заголовков; ничего в UI и ротации при этом не меняется.

`RotateOn` — то, что делает «минимальный лимит настраиваемым только там, где
он есть» структурным свойством, а не проверкой в трёх местах: поле порога
рисуется, валидируется и читается ровно под `RotateThreshold`.

### 5.2 Активная учётка и рантайм

Ротация не должна трогать пути сборки провайдеров — там уже есть корректная
инвалидация. Поэтому активная учётка **проецируется** в существующий
`ProviderConfig`:

```
accounts.Store ──выбор активной──▶ ConfigStore.UpdateProviderCredentials(
                                       providerID, token.AccessToken, token)
                                   + провайдерский ProxyURL := account.ProxyURL
```

`UpdateProviderCredentials` уже поднимает `credentialVersion`, что заставляет
`runtime_builder` пересобрать провайдера с новыми креденшелами. Понадобится
одно расширение: метод должен уметь публиковать и `ProxyURL`, и вызывать
`SetupCodex()` (сейчас он вызывает только `SetupGitHubCopilot`) — иначе после
смены учётки в заголовке останется `chatgpt-account-id` прошлой.

Это самая аккуратная точка вмешательства: ниже по стеку (`runtime_builder`,
`fantasy`) не меняется ничего.

### 5.3 Прокси: разрешение

```
account.ProxyURL != ""  → он
иначе provider.ProxyURL != "" → он
иначе                   → HTTP_PROXY/HTTPS_PROXY (текущее поведение)
```

Значение `none` на любом уровне = принудительно прямое соединение (уже
поддержано `proxyhttp.Direct`). Функция разрешения — одна, в `accounts`, и
используется всеми: логином (`login_codex.go`), refresh'ем
(`credentials.providerProxy`), сборкой рантайма и фоновым опросом лимитов.

### 5.4 Лимиты: снятие singleton'а

`internal/oauth/codex/usage.go` сейчас держит один снимок на процесс. Меняем
на map по `accountID`:

```go
func RecordUsageFor(accountID string, u Usage)
func UsageFor(accountID string) (Usage, bool)
func LatestUsage() (Usage, bool)   // остаётся: снимок последнего активного
```

`usageTransport` знает свой accountID (он его же шлёт в заголовке), поэтому
пишет и в map, и в `latestUsage`. `LatestUsage()` сохраняется — сайдбар и
`provider_log.go` не трогаем.

Дополнительно нужен способ узнать лимиты учётки, которой сейчас не
пользуемся: лёгкий запрос к `/models` (уже есть `codex.FetchModels`) от имени
учётки возвращает те же `X-Codex-*` заголовки. Это даёт «Обновить» в диалоге
и опрос кандидатов при ротации. Опрос — только по явному действию и при
ротации, никакого фонового поллинга по таймеру.

### 5.5 Ротация

Два триггера с общим механизмом выбора.

```go
type Rotator struct { store accounts.Store; cfg RotationConfig }

// ShouldRotate (RotateThreshold): активная учётка за порогом хотя бы по
//       одному известному окну.
// MarkRateLimited (RotateRateLimit): пометить учётку остывающей до
//       time.Now()+Retry-After (иначе +cooldown из конфига).
// Pick: следующая по order, не disabled, не остывающая, с известным usage
//       под порогом. Неизвестный usage — считается пригодной (оптимистично:
//       узнаем из первого же ответа).
//       Если пригодных нет — ErrAllExhausted{ResetsAt} (Р4): запрос не
//       отправляется, пользователь видит «все учётки исчерпаны, ближайший
//       сброс в HH:MM». Для 429-провайдеров ResetsAt — минимум из времён
//       остывания.
```

**Триггер по порогу (Codex).** Вызов после завершения запроса, там же где
читаются usage-заголовки: транспорт пишет снимок, агент между шагами
спрашивает `ShouldRotate()`. Смена — через §5.2, с событием в UI
(«Codex: переключено на "Рабочий", у "Личный" осталось 8%»).

**Триггер по 429 (все остальные).** Здесь есть препятствие в форке fantasy:
`OnAuthRefresh` вызывается только на 401/`AuthError`
(`third_party/fantasy/retry.go`, функция `isAuthError`), а 429 считается
обычной retryable-ошибкой и уходит в экспоненциальный бэкофф, не доходя до
хука. Значит нужен парный хук, симметричный существующему:

```go
// RetryOptions
OnRateLimit OnRateLimitFunc // вызывается при 429; nil → пасс повторяется
                            // с новым бюджетом (как OnAuthRefresh)
```

Реализация в `internal/agent` рядом с `makeAuthRefreshCallback`
(`runtime_builder.go:564`): пометить текущую учётку остывающей, выбрать
следующую, опубликовать её через §5.2, пересобрать рантайм — и вернуть nil,
чтобы fantasy повторила шаг уже с новой учёткой. Если `Pick` вернул
`ErrAllExhausted`, хук возвращает ошибку и наружу идёт исходный 429.

Форк вендорится через `replace` в `go.mod` и уже правился под Sennit
(см. комментарий про 401 в `third_party/fantasy/errors.go`), так что правка
законна; её надо держать минимальной и описанной в NOTICE-стиле рядом.

Защиты:
- не чаще одной ротации в N секунд (антидребезг на серии быстрых ответов);
- ротация по порогу не запускается во время активного стрима — только между
  шагами. Ротация по 429 неизбежно происходит внутри retry-пасса, но это
  безопасно: 429 приходит до полезного вывода, а `OnRetry` в fantasy уже
  обязывает потребителей сбрасывать накопленный стрим (см. доккоммент
  `OnRetryCallback`) — проверить, что этот сброс отрабатывает и на нашем
  пути;
- не больше одной ротации на один retry-пасс, чтобы перебор из пяти учёток
  не превратился в пять полных бэкоффов;
- если учётка одна, весь механизм — no-op;
- `ErrAllExhausted` — «мягкая» ошибка сессии: она не роняет агента и не
  портит тред, а показывается как сообщение с временем сброса, чтобы можно
  было продолжить позже или переключиться на другого провайдера вручную.

## 6. UI

### 6.1 Новый диалог «Учётки провайдера» (`internal/ui/dialog/accounts.go`)

Открывается из существующего диалога провайдеров (`providers.go`): выбор
провайдера ведёт не сразу в OAuth/ввод ключа, а в список его учёток. Диалог
один на все провайдеры; колонки лимитов и пункт настройки ротации рисуются
только когда `CapabilitiesOf(providerID).Usage` (§5.1).

```
┌ OpenAI Codex — учётки ────────────────────────────┐
│ ● Личный Plus        plus   нед. 42%  час 7%      │
│ ○ Рабочий Pro        pro    нед. 91%  час 3%  ⚠   │
│ ○ Запасной           —      лимиты неизвестны     │
│                                                    │
│ + Добавить учётку                                  │
│ ⚙ Настройки провайдера (прокси, ротация)          │
└ enter активировать · e изменить · d удалить · r обновить лимиты ┘
```

- `enter` — сделать активной (§5.2);
- `e` — форма учётки: label, прокси (с валидацией `codex.ValidateProxy`),
  вкл/выкл;
- `d` — удалить (с подтверждением; удаление активной переводит на следующую);
- `r` — обновить лимиты (запрос `/models` от имени учётки, с её прокси);
  для провайдеров без лимитов пункт не показывается;
- `+` — по `AuthKind`: для Codex/Copilot существующий OAuth-флоу
  (`oauth_codex.go`), для api-key-провайдеров — существующая форма ключа
  (`api_key_input.go`). В обоих случаях результат кладётся **новой** учёткой,
  а не перетирает текущую. Дубль (по `account_id` для OAuth, по значению
  ключа для api-key) — предупреждение вместо создания второй записи.

Для провайдера без лимитов строки выглядят проще, а вместо процентов
показывается состояние остывания после 429:

```
┌ opencode — учётки ────────────────────────────────┐
│ ● Рабочий ключ       sk-…4f2a   прокси: прямое    │
│ ○ Личный ключ        sk-…9b10   429, до 14:20  ⏳ │
│                                                    │
│ + Добавить учётку                                  │
│ ⚙ Настройки провайдера (прокси, ротация по 429)   │
└ enter активировать · e изменить · d удалить ──────┘
```

### 6.2 Настройки провайдера

Маленькая форма, содержимое зависит от `RotateOn` (§5.1):

| Поле | `RotateThreshold` (Codex) | `RotateRateLimit` (opencode и пр.) |
| --- | --- | --- |
| Общий прокси | да | да |
| Ротация вкл/выкл | да | да |
| Порог остатка, % | да, по умолчанию 10 | **поля нет** |
| Cooldown после 429 | нет | да, по умолчанию 10 мин |
| Порядок обхода | да | да |

Поле порога не просто скрыто — при `RotateRateLimit` оно не существует ни в
форме, ни в конфиге, ни в схеме, и заданное руками отвергается валидацией
(§4). Под строкой ротации — поясняющая подпись: «переключение при остатке
ниже порога» либо «переключение при ответе 429».

### 6.3 Сайдбар

К строке плана добавляется label активной учётки, когда их больше одной:
`plus · Личный Plus · нед. 42%`. Правки — в `common.FormatPlanUsage` и
`sidebar.go`.

## 7. CLI

- `sennit auth list [provider]` — список учёток (с лимитами там, где они есть);
- `sennit auth use <provider> <account>` — переключить;
- `sennit auth add <provider>` — то же, что `login`, но добавляет учётку;
  для api-key-провайдера принимает ключ (`--api-key`, иначе спрашивает);
- `sennit auth remove <provider> <account>`;
- `sennit auth proxy <provider> [<account>] <url|none|->` — задать/снять прокси.

`sennit login codex` сохраняется как есть: без учёток создаёт первую, при
наличии — добавляет ещё одну (поведение печатается явно).

## 8. Фазы работ

Каждая фаза — самостоятельный коммит, зелёные тесты, ничего не сломано для
пользователя с одной учёткой.

**Ф1. Хранилище.** Пакет `internal/providers/accounts`: модель, реестр
возможностей, файловый Store с атомарной записью и локом, миграция из
`providers.<id>` (и OAuth-, и api-key-провайдеров).
*Готово, когда:* юнит-тесты на конкурентную запись двух процессов, на
миграцию, на права файла; `sennit` с одной учёткой работает как прежде.

**Ф2. Лимиты per-account.** `usage.go` → map по accountID, `UsageFor`,
сохранение снимка в Store, функция разового опроса лимитов через `/models`.
*Готово, когда:* тест, что два accountID не затирают снимки друг друга;
`LatestUsage()` и сайдбар не изменили поведение.

**Ф3. Переключение + прокси.** Проекция активной учётки в `ProviderConfig`,
`UpdateProviderCredentials` учит `SetupCodex` и `ProxyURL`, единая функция
разрешения прокси, подключение к `login_codex`/`credentials.exchange`.
*Готово, когда:* тест «переключение учётки меняет `chatgpt-account-id` и
поднимает `CredentialVersion`»; тест приоритета прокси (учётка > провайдер >
env); ручная проверка на двух реальных учётках.

**Ф4. UI.** Диалог учёток, форма учётки, форма настроек провайдера, вход из
`providers.go`, метка учётки в сайдбаре.
*Готово, когда:* golden-тесты диалогов по образцу `providers_test.go` — в
двух вариантах, с лимитами (Codex) и без (api-key провайдер);
`uncovered_dialogs_test.go` не жалуется на новый диалог.

**Ф5a. Ротация по порогу (Codex).** `Rotator`, `ShouldRotate`/`Pick`, вызов
между шагами агента, антидребезг, событие в UI, `ErrAllExhausted` (Р4).
*Готово, когда:* табличные тесты `ShouldRotate`/`Pick` (порог, disabled,
неизвестный usage, все исчерпаны → ошибка с ближайшим `ResetsAt`); тест, что
стрим не прерывается; тест, что у провайдера с `RotateRateLimit` порог не
читается и не валидируется.

**Ф5b. Ротация по 429.** Хук `OnRateLimit` в `third_party/fantasy/retry.go`,
его реализация рядом с `makeAuthRefreshCallback`, учёт `Retry-After` и
cooldown, лимит «одна ротация на retry-пасс».
*Готово, когда:* тест форка — 429 доходит до хука, 401 по-прежнему до
`OnAuthRefresh`, обе ошибки не путаются; тест, что после ротации повторный
шаг уходит с новым ключом; тест, что при всех остывающих наружу идёт
исходный 429, а не подменённая ошибка.

**Ф6. CLI и документация.** Команды `sennit auth …`, страница в `docs/`,
обновление `schema.json` (генерится — см. `internal/cmd/schema.go`).

Оценка: Ф1–Ф3 — костяк, без них ничего не видно; Ф4 — самая объёмная по
коду, но наименее рискованная; Ф5 требует аккуратности с моментом вызова.

## 9. Риски

1. **Refresh-лок на провайдера, а не на учётку.** `RefreshLockPath(providerID)`
   сериализует refresh разных учёток между собой. Не ошибка, но узкое место —
   в Ф3 ключ лока расширяется до `providerID+accountID`.
2. **Single-use refresh token Codex CLI.** Логика «не тратить токен CLI»
   (`TokenFromDiskFor`) завязана на один accountID. При нескольких учётках
   импорт с диска относится только к той, чей accountID совпал, — это уже
   заложено в текущем коде и должно сохраниться.
3. **Ротация и посреди-сессионная смена аккаунта.** Контекст диалога не
   переносится между аккаунтами на стороне Codex, но и не должен: запросы
   stateless. Проверить только, что смена не роняет кэш промпта заметно для
   пользователя (Ф5, ручная проверка).
4. **Секреты на диске.** `accounts.json` c refresh-токенами: права 0600,
   отсутствие в логах (`internal/agent/provider_log.go` уже маскирует
   креденшелы — проверить, что новые поля тоже не попадают).
5. **`api_key` как шаблон.** У api-key-провайдеров значение ключа может быть
   не литералом, а `$VAR`/`$(cmd)`: `ProviderConfig` хранит для этого
   `APIKeyTemplate` и переразрешает его на ошибках авторизации
   (`runtime_builder.go:606`). Учётка должна хранить **шаблон**, а не
   разрешённое значение, иначе переключение зафиксирует протухший ключ. В UI
   такую учётку показывать по шаблону (`$OPENAI_API_KEY`), а не по хвосту
   ключа.
6. **Правка вендоренного fantasy.** `OnRateLimit` — изменение в
   `third_party/fantasy`, которое придётся переносить при обновлении
   апстрима до v0.41+. Держать патч в одном файле, рядом с существующим
   `OnAuthRefresh`, и не менять сигнатуры существующих типов.
7. **Retry перезапускает шаг целиком.** `OnRetryCallback` в fantasy прямо
   предупреждает: колбэки стрима фаярятся заново с начала, и потребитель
   обязан сбросить накопленное. Ротация по 429 ходит этим же путём, поэтому
   в Ф5b нужен тест именно на отсутствие склейки двух ответов.
8. **Windows.** Атомарный `rename` поверх существующего файла и файловые
   права ведут себя иначе; `scripts/check_cross_platform.sh` и уже
   существующая практика скипа таких тестов на Windows.

## 10. Открытые мелочи

Не блокируют старт, решаются по ходу:

- нужен ли per-project override активной учётки (сейчас — только глобальный);
- показывать ли в диалоге баланс/лимиты api-key-провайдеров, если кто-то из
  них отдаёт их в заголовках (проверить при Ф2, пока считаем, что нет);
- поведение `sennit auth use` при неактивной (disabled) учётке — сейчас
  предполагается отказ с подсказкой включить.
