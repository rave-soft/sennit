Снимок на `6a22f6da`, ревизия на `944d4339`. Этот документ **заменяет**
предыдущий план (ревью на `12662b01`, статус на `f598276f`): те фазы 1–4
закрыты почти целиком, а их незакрытый остаток перенесён сюда в §7. Историю
прошлого плана смотреть в `git log -- ARCHITECTURE_REVIEW.md`.

**Ревизия от 2026-08-15.** Приняты два решения владельца, меняющие план:

1. **Braid больше не ориентируется на upstream** (`charmbracelet/crush`).
   Git remote удалён. «Удобство diff с форк-источником» перестало быть
   аргументом при выборе решений. Лицензионную атрибуцию в `README.md` и
   `LICENSE.md` это не затрагивает.
2. **Клиент-серверный режим удаляется целиком** — см. C1. Это переворачивает
   главный пункт плана: вместо генерации шва воркспейса мы убираем то, ради
   чего шов существовал. **Выполнено в тот же день** (`027d6155`).

Статус пунктов отмечен в §4–§6 маркерами ✅ / 🟡 / ❌.

Прошлый план решал задачу «баги, гонки, отзывчивость, копипаста». Он свою
работу сделал. Оставшаяся проблема была структурная: **добавление одной
операции воркспейса стоило правок в шести местах, а три объекта (UI,
ConfigStore, sessionAgent) держали по четыре ответственности каждый**. Первую
половину закрыл C1 — точек касания осталась одна. Все три перегруженных
объекта разобраны: `sessionAgent` (S3), `UI` (S1) и `ConfigStore` (C5).
Этот план — про границы, а не про баги.

## 1. Принципы и правила приёмки

| Принцип | Как применяем здесь | Как проверяем |
|---|---|---|
| **SRP** | У типа одна причина меняться. Практический порог: тип > 800 строк или > 30 методов — кандидат на разрез, но режем по ответственности, не по строкам | Разрез считается удавшимся, если новый файл собирается без обратного импорта в исходный |
| **OCP** | Новая операция/тул/диалог добавляется расширением реестра, а не правкой шести файлов | Считаем «точки касания» на добавление одной операции; цель — ≤ 2 |
| **LSP** | Никаких optional-интерфейсов через `type assertion` там, где вызывающий обязан знать реализацию | Убрать вопросы вида «а этот воркспейс умеет треды?» из вызывающего кода в capability-снимок |
| **ISP** | Зависимость объявляет тот минимум, что реально зовёт. Тул не получает `*config.ConfigStore` целиком ради двух полей | Конструктор принимает узкий интерфейс, объявленный **на стороне потребителя** |
| **DI** | Зависимости передаются, не берутся из пакета-синглтона | Пакет тестируется без `t.Setenv` и без глобальных путей |
| **DRY** | Дедуплицируем **знание**, а не совпадающий текст. Симметричные слои client/server были одним знанием в шести копиях — вылечено удалением (C1) | Одно изменение контракта = одна правка |
| **KISS** | Предпочитаем удалить абстракцию, чем добавить | Каждый пункт плана обязан уменьшать суммарный размер или число точек касания |
| **YAGNI** | Не строим уровни под гипотетические сценарии. §8 — явный список того, что **не** делаем | Пункт без сегодняшнего потребителя не попадает в фазы |

**Правило PR.** Один пункт плана = один PR. Зелёные тесты обязательны, поведение
не меняется (кроме пунктов, помеченных «поведенческий»). Рефакторинг и
изменение поведения в одном PR — запрещено: это лишает нас единственной
страховки.

Фактические контексты по коду (не по каталогам):

Диагноз по швам (снят на `6a22f6da`; пункты 1, 2 и 3 с тех пор закрыты):

5. ❌ **`config` — общий знаменатель всего.** От него зависят agent, tools,
   lsp, ui, thread, commands, hooks. При этом внутри он же хранит OAuth-токены
   и умеет их обновлять по сети. Открыто — см. C5.

## 3. Целевые границы

```
ui/*            → только workspace + proto (DTO) + ui/presentation + ui/styles
cmd/*           → workspace + config (чтение)
workspace/*     → AppWorkspace (логика) + readOnlyWorkspace (декоратор)
proto/*         → словарь DTO; ни сериализации, ни маршрутов
thread/*        → домен делегаций; app подставляется через Spawner (уже есть)
agent/*         → runtime агента; не знает про транспорт и UI
config/*        → расщеплён: config (данные) / credentials (OAuth) /
                  providers (каталог+дискавери) / configmigrate (миграции)
```

Правило направления: **frontend → façade → domain → infra**.
Обратных стрелок нет. Единственное исключение — `app` как композиционный
корень, ему можно всё.

### C2. `thread` → `app`: перевёрнутая зависимость ✅

**Закрыто** (`904ddc40`): `go list -deps ./internal/thread` не содержит ни
`internal/app`, ни `internal/db`. Логика, требующая `*app.App`, живёт в
`internal/app/threadspawn`.

**Проблема (была).** `internal/thread` импортирует `internal/app` в четырёх файлах.
`thread.Spawner` (из п. 4.4 прошлого плана) уже даёт правильную инверсию, но
`manager.go`/`lifecycle.go` продолжают ходить в `app` напрямую.

**Действие.** Всё, что требует `*app.App`, вынести в `internal/app/threadspawn`
(или в `backend`), оставив в `thread` только доменные интерфейсы `Spawner`/
`Handle`. `internal/thread` не должен импортировать ни `app`, ни `db`.

**Готово, когда** `go list -deps internal/thread` не содержит `internal/app`
и `internal/db`.

**Риск:** средний (затрагивает lifecycle тредов — исторически хрупкое место).
Обязательны существующие ownership/state-machine тесты в зелёном.

### C3. UI ходит мимо фасада ✅

**Закрыто** (`782d0ce6`): правило `ui-boundary` в `.golangci.yml:35-44` с
инвентаризацией в комментарии. После C1 из deny-листа уйдут исчезнувшие

**Проблема (была).** `ui/model` импортирует `agent`, `thread`, `permission`, `lsp`,

неизбежна (типы событий), часть — прямой доступ к домену в обход `Workspace`.

**Действие.**
1. Инвентаризовать каждый доменный импорт `ui/model`: «тип события / DTO» —
   допустимо; «вызов логики» — переносится за фасад.
2. Зафиксировать правило `depguard` в `.golangci.yml`: `internal/ui/**` не
   импортирует `internal/agent`, `internal/thread`, `internal/backend`,
   `internal/db`, `internal/app`, `internal/server`, `internal/client`.

**Готово, когда** линтер зелёный без исключений на `agent`/`thread`/`db`.

**Риск:** низкий, но объёмный по числу мелких правок.

### C4. Граница `proto` не описана ✅

**Закрыто:** правило записано в `AGENTS.md:70-73`. После C1 требует одной
правки формулировки: `proto` перестаёт быть транспортом, довод «тянет
транзитивные зависимости в провод» исчезает, остаётся только довод про типы
с поведением.

**Проблема (была).** `proto` алиасит доменные типы. Это дёшево и работает, но
правило нигде не записано, и каждый новый тип — спор заново.

**Действие (документ, не код).** Записать правило в `AGENTS.md`: `proto` может
алиасить **leaf-типы данных** (`message`, `session`, `skills`), но не типы с
поведением и не типы, тянущие транзитивные зависимости (`config`, `agent/tools`,
`lsp`). Для последних — явные DTO в `proto`. Пересмотреть три текущих нарушения
(`agent/tools`, `config`, `lsp`) и либо узаконить, либо перевести на DTO.

**Риск:** минимальный. **Это не YAGNI-абстракция, а фиксация уже принятого
решения** — стоимость нулевая, экономия на каждом будущем PR.

### C5. `config` держит четыре контекста ✅

**Закрыто** (`020fe1a3`, `38493fcd`, `3c76b191`). Оба критерия выполнены:
`credentials` тестируется без `config.Load`, а `config.go`+`store.go`+`load.go`
дают **2 007 строк** при цели < 2 500 (было 4 667). `ConfigStore` — 800 строк
и 36 методов вместо 1 630 и 60+.

**Что получилось не так, как планировалось.** Плановый порядок
`providers → credentials` оказался неисполнимым в первой половине.
`config/providers` отдельным пакетом не становится: `Load` вызывает
`mergeCatalogProviders`/`discoverCustomProviderModels`/`validateCustomProviders`,
а тем нужны `Config`, `ProviderConfig`, `VariableResolver` обратно — цикл.
Пакетом провайдеры станут только после переноса общих типов в leaf-пакет;
это отдельное решение, а не побочный эффект C5. Поэтому провайдеры разрезаны
по файлам внутри `config`.

С `credentials` наоборот: внутри пакета кластер не вызывает никто, все
потребители снаружи. Пакет выделен по-настоящему — но ценой того, что
делегирующие методы пришлось **убрать** с `ConfigStore`, иначе `config`
начал бы импортировать `config/credentials` и цикл вернулся бы с другой
стороны.

| Итог | Что внутри |
|---|---|
| `config/credentials` (414) | `Manager` за семиметодным интерфейсом `Store`: refresh, single-flight, кросс-процессные локи, обмен токенов, `ImportCopilot`, рукопожатие интерактивной авторизации |
| `config` (по файлам) | `providers_{merge,discover,validate}.go`, `agents.go`, `staleness.go`, `reload.go`, `mcp_token.go`, `paths.go`, `defaults.go` |
| `config/migrate` | было сделано раньше |

**Нашлось при разборе — и это главное в пункте.** `SignalAuthComplete` зовёт
`workspace`, а `WaitForTokenChange` ждёт `agent`, и общаются они через карту
каналов, приватную для одного `Manager`. Раньше единственность держалась на
том, что `*ConfigStore` — синглтон. После выделения пакета два экземпляра
не упали бы с ошибкой: агент просто повис бы на пятиминутном таймауте.
Поэтому `Manager` создаётся один раз в `app.New`, раздаётся через
`App.Credentials()`, а `TestSharedCredentialsManager` прогоняет настоящий
сигнал сквозь продакшен-аксессоры обеих сторон.

**Единственное, что не является переносом** — `ConfigStore.PersistRefreshedToken`.
Хвост `refreshOAuthTokenLocked` собирал ключи через `ProviderFieldKey` и
сверялся с `isCatalogProvider`; это знание о форме конфига, и вынести его в
`credentials` значило бы экспортировать `update` и `isCatalogProvider` наружу,
то есть отдать сырые примитивы вместо шва. Восемь из десяти перенесённых
функций совпадают с оригиналом побайтово.

**Риск был средний-высокий, реализовался в одном месте:** ровно в вопросе
единственности `Manager`, и был снят тестом до, а не после.

угадать за письменным столом — его надо снять грепом с места употребления,

`ConfigStore` вместо фейков. Интерфейсы это теперь позволяют, но подмена
тестовых двойников — отдельная работа со своим риском, а не хвост этого
пункта.

**Риск:** оценивался как низкий, реализовался нулевой — все изменённые
строки являются подменой типа.

1. Линтер `unused` **не отключён**: в `.golangci.yml` в `disable:` стоит

## 8. Что мы осознанно НЕ делаем (YAGNI)

- **Не вводим слой доменных событий / CQRS / шину поверх `pubsub`.** Текущего
  брокера хватает, второго потребителя нет.
- **Не делаем `proto` полностью независимым от домена.** Конверторы уже
  удаляли один раз (п. 4.5) — возвращать их ради чистоты границы дороже пользы.
  Ограничиваемся правилом C4. После C1 довод усиливается: сериализовать
  больше нечего.
- **Не восстанавливаем клиент-серверный режим** под гипотетические веб-морду,
  ACP или «агент работает с закрытым ноутом». Если такой сценарий появится,
  его проектируют заново под реальные требования, а не откатывают C1.
- **Не строим «фреймворк тулов»** с общим базовым типом. Узкие интерфейсы (S4)
  дешевле и не связывают тулы друг с другом.
- **Не схлопываем интерфейс `Workspace` в конкретный тип.** Пункт стоял в
  фазе D с обоснованием «реализаций две, и вторая — декоратор». Посылка
  неверна: кроме `AppWorkspace` и `readOnlyWorkspace` интерфейс реализуют
  **восемнадцать тестовых дублей** в `ui/model` и `ui/dialog`
  (`cmdDrivingWorkspace`, `testWorkspace`, `threadsTestWorkspace`,
  `apiKeyTestWorkspace` и другие). Это и есть причина интерфейса быть: он —
  шов, на котором мокается весь UI-тестсьют, включая golden-снимки из S1.
  Схлопывание заставило бы каждый такой тест поднимать настоящий
  `AppWorkspace` с базой, конфигом и агентом, то есть обменяло бы
  архитектурную аккуратность на медленные нештатные тесты.

  Заодно снят вопрос о ширине: интерфейс давно не монолит, а композиция из
  тринадцати ролевых (`SessionStore`, `AgentController`, `MCPController`,
  `ThreadController` и так далее), а дубли встраивают `workspace.Workspace`
  и переопределяют только нужное. То есть ISP здесь уже соблюдён.
- **Не выделяем `internal/domain`.** Пакеты `session`/`message`/`permission`
  уже leaf и уже правильно направлены; переезд даст только шум в diff.
- **Не мигрируем UI на другую архитектуру** (Elm-модули, отдельные Program).
  S1 достаточно.
- **Не трогаем `event`-каркас** (девять no-op вызовов — дешевле, чем охота по
  девяти файлам, если появится свой сток) и не превращаем `Recover` в
  распределённый протокол — решения прошлого ревью остаются в силе.
- **Copilot ToS** и политика хуков для под-агентов — решения владельца
  проекта, не задачи рефакторинга (см. `TECHDEBT.md`).

недостижимая без потери этой гарантии.
