# Этап 1.5. Спайк: доставка steering рядом с tool result

Дата: 2026-08-14. Библиотека: `charm.land/fantasy v0.40.0`.

## Вопрос

План предполагал, что steering-текст нужно доставлять **в том же user
message, что и tool result**, отдельным текстовым блоком, и что для
этого потребуется правка в Braid или в адаптере. Спайк должен был
проверить, какие провайдеры такое совмещение принимают.

## Ответ

Совмещение делать не нужно: там, где оно требуется, `fantasy` выполняет
его само, а там, где не требуется, раздельные сообщения легальны.
Текущая реализация Braid — добавить отдельный `user` message после всех
tool results — даёт корректный запрос для трёх семейств из четырёх.

| Провайдер | Что уходит на провод | Статус |
|---|---|---|
| Anthropic | **Один** user message с блоками `[tool_result…, text…]` | Подтверждено по исходникам |
| OpenAI-compatible (chat completions) | `role:"tool"`, затем отдельный `role:"user"` | **Подтверждено живым запросом** |
| OpenAI Responses | `function_call_output` item, затем отдельный user input item | Следует из структуры API, живьём не проверено |
| Google / Gemini | Два подряд идущих `Content{Role: user}` | **Риск, не проверено** |

## Обоснования

### Anthropic — совмещение уже происходит

`providers/anthropic/anthropic.go`, функция `groupIntoBlocks`
(строки 505–550): сообщение с ролью `Tool` присоединяется к текущему
блоку, если тот имеет роль `User`, а следующее сообщение с ролью `User`
присоединяется к тому же блоку. Далее (строки 897+) содержимое всего
блока — и `tool_result`, и текстовые части — выкладывается в один
`anthropicContent`, то есть в одно user message.

Иначе говоря, последовательность `tool(tool_result) → user(steering)`,
которую Braid формирует сегодня в `prepareStep`, уже превращается в
целевую форму на уровне провода. Отдельная работа по «прикреплению
steering к блоку tool result» в Braid не нужна и была бы вредной:
она продублировала бы то, что адаптер делает сам, и сломала бы
провайдеров, где нужна именно раздельная форма.

### OpenAI-compatible — проверено живьём

Запрос вида `user → assistant(tool_calls) → tool → user(steering)`
отправлен на локальный OpenAI-совместимый эндпоинт (`qwen36-local`,
модель `local/Qwen3.6-35B-A3B`): ответ **200**, и модель выполнила
именно steering-инструкцию, а не только исходный запрос.

### OpenAI Responses — структурно безопасно

`providers/openai/responses_language_model.go` (строка 579+): tool
results становятся отдельными item'ами `function_call_output`, а
пользовательский текст — отдельным input item. Раздельность здесь
является нормой протокола, а не обходным путём.

### Google / Gemini — единственное место риска

`providers/google/google.go` (строки 484–555): результаты инструментов
собираются в `genai.Content{Role: user, Parts: [FunctionResponse…]}`,
а следующее user-сообщение (строка 410) создаёт **второй** такой же
`Content{Role: user}`. Слияния подряд идущих однорольных Content нет ни
в адаптере, ни на стороне Braid (`workaroundProviderMediaLimitations`
занимается другим).

Gemini в ряде случаев отвечает 400 на непеременяющиеся роли в
`contents`. Примет ли он два подряд идущих user-контента в этой
конкретной форме — вопрос эмпирический, ключа для проверки нет.

## Что это меняет в плане

- **Этап 2 упрощается.** Пункт «прикреплять drained steering к user
  message с tool results» следует убрать: для Anthropic это уже так, а
  для остальных раздельная форма и есть правильная. Оставить текущее
  поведение `prepareStep`.
- **Остаётся один рабочий пункт:** проверить Gemini и, если он
  отвергает два подряд идущих user-контента, слить их — в адаптере
  `fantasy` либо нормализацией на стороне Braid перед вызовом.
- Fallback-схема из плана (отдельный `user` message после tool results)
  оказалась не запасным вариантом, а основным.

## Незакрытое

Живая проверка Anthropic, OpenAI Responses и Gemini требует ключей;
в окружении их нет. Для Gemini это существенно — там реальный риск.
Для первых двух проверка носит подтверждающий характер: форма запроса
следует из исходников и из устройства протокола.
